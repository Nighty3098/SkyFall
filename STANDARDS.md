# Стандарты коммитов и Pull Request (PR)

> [!summary] Для чего это нужно?
> Чистая история изменений, быстрое код-ревью и автоматическая генерация `CHANGELOG`. Основано на [[Conventional Commits]] и командных практиках.

## 1. Стандарты коммитов

### Формат (Conventional Commits)

```text
<тип>(<область>): <краткое описание>

<тело сообщения (опционально)>
<footer (опционально)>
```

### Типы коммитов (`type`)

| Тип        | Назначение                       | Пример                               |
| ---------- | -------------------------------- | ------------------------------------ |
| `feat`     | Новый функционал                 | `feat(auth): add login via Google`   |
| `fix`      | Исправление бага                 | `fix(api): handle null response`     |
| `docs`     | Документация                     | `docs: update README setup guide`    |
| `style`    | Форматирование (код не меняется) | `style: fix indentation`             |
| `refactor` | Улучшение кода без фич/багов     | `refactor(user): extract validation` |
| `test`     | Добавление/правка тестов         | `test(cart): add unit tests`         |
| `chore`    | Обновление сборки, зависимостей  | `chore: bump lodash to 4.17.21`      |
| `ci`       | Настройка CI/CD                  | `ci: add GitHub Actions workflow`    |
| `perf`     | Улучшение производительности     | `perf(store): lazy load images`      |
|            |                                  |                                      |

> [!tip] Правила хорошего коммита
> - Длина заголовка **≤ 50 символов**.
> - Используй **повелительное наклонение** (Add, Fix, Update).
> - Без точки в конце заголовка.
> - Один коммит = одно логическое изменение.

## 2. Стандарты Pull Request (PR)

### Структура описания (шаблон)

```markdown
## Тип изменения
- [ ] bugfix
- [ ] feature
- [ ] refactor
- [ ] docs

## Описание
Что делает этот PR? Какую проблему решает?

## Связанные задачи
Closes #123

## Как протестировать?
Шаги для проверки

## Checklist
- [ ] Код по style guide
- [ ] Есть тесты
- [ ] Обновлена документация
```

> [!info] Где хранить шаблон?  
> В корне репозитория: `.github/pull_request_template.md`

### Правила для PR

| Что               | Как                                          |
|-------------------|----------------------------------------------|
| **Размер**        | Не больше 400–500 строк. Иначе → разбить     |
| **Название**      | Чёткое, как заголовок коммита                |
| **Линковка**      | Привязывай к [[Issues]] или задаче           |
| **Draft PR**      | Если не готово к ревью                       |
| **CI/CD**         | Все проверки должны проходить успешно        |

> [!quote] Во время ревью
> Будьте вежливы. Мержите только после апрува.

## 3. Плохо → Хорошо (примеры)

### Коммиты

| ❌ Плохо                     | ✅ Хорошо                                 |
|-----------------------------|-------------------------------------------|
| `fixed stuff`               | `fix(parser): handle empty CSV rows`      |
| `новое`                     | `feat(ui): add dark theme toggle`         |
| `Update 3 files`            | `refactor(auth): extract JWT validation`  |

### PR

| ❌ Плохо                            | ✅ Хорошо                                   |
|-------------------------------------|---------------------------------------------|
| Название: `Правки`                  | Название: `Add password reset via email`   |
| Описание: пустое                    | Описание: + шаги тестирования, ссылка на задачу |
| 1500 строк изменений                | 300 строк, разбито на логические коммиты    |

## 4. Инструменты для автоматизации

- `Commitlint` → проверка формата коммитов
- `Husky` → хуки перед коммитом
- `Semantic Pull Request` → бот для проверки PR
- [[Conventional Commits]] → официальная спецификация
